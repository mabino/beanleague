1. Database Schema (SQLite)
Since you are self-hosting for a small group, SQLite is the perfect low-overhead choice. The schema needs to decouple the external API data from the internal game logic so your son's league can operate independently of how the data is fetched.
players: The central directory.
Columns: id (Primary Key matching the external API ID), name, real_team_id, position (GK, DEF, MID, FWD), current_price, status (Active, Injured).
fixtures: The real-world match schedule.
Columns: id, home_team_id, away_team_id, kickoff_time, status (Scheduled, In-Play, Finished).
player_match_stats: The core scoring table. This is what your cron job writes to.
Columns: id, player_id, fixture_id, minutes_played, goals, assists, clean_sheet, yellow_cards, red_cards, fantasy_points_calculated.
leagues: The virtual leagues created by the kids.
Columns: id, season_code (e.g., BARCA-2026), name, max_teams.
teams: The kids' fantasy teams.
Columns: id, league_id, manager_code (their login PIN), team_name, total_points.
rosters: The mapping of real players to the kids' teams.
Columns: id, team_id, player_id, is_starting_xi (Boolean), is_captain (Boolean).

3. Login-Less Authentication Engine
To keep it frictionless for 12-year-olds without requiring email signups, use a token-based system relying on shared and personal codes.
The Season Code (The Room): You generate a code (like a Kahoot PIN, e.g., LA-LIGA-26) and give it to your son. Anyone who enters this code on the landing page joins that specific league environment.
The Manager Code (The Key): When a friend joins via the Season Code, they are prompted to create a team name and are assigned a 6-digit Manager Code (e.g., 849-201).
Session Management:
The web app stores the Manager Code in the browser's localStorage.
Whenever the frontend requests data to modify a roster or view a team, it passes this code in the Authorization header.
If they switch devices (like moving from an iPad to a PC), they simply click "Existing Manager," type their 6-digit code, and the app retrieves their team from the SQLite teams table.

Here are the missing operational and architectural layers:
The Player Acquisition Model (Game Mechanics)
Right now, the database allows teams to have players, but there is no rule stopping all the kids from picking Lamine Yamal and Erling Haaland. You must build a constraint system:
Salary Cap: Assign a virtual dollar value to every player (e.g., $100M budget per team). This requires adding a price column to the players table and building a frontend validator that blocks roster saves if the budget is exceeded.
Draft System: Alternatively, build a one-time "draft room" interface where players are locked to a single team once picked. This requires a WebSocket server (like Socket.io) for real-time draft picks so the kids see players disappear from the board instantly.
The Scoring Engine (Asynchronous Worker)
The cron job handles fetching raw stats, but a separate process must convert those stats into fantasy points.
Create a "Scoring Engine" script that runs immediately after the Matchday Poller finishes.
It reads the raw goals, assists, and clean_sheets in player_match_stats, applies your custom multipliers (e.g., goals by defenders are worth more than goals by forwards), and writes the final integer to fantasy_points_calculated.
It then aggregates those points and updates the teams.total_points field so the leaderboard is ready for the frontend to read.
External Access & Networking
Since your son's friends will be playing from their own houses on their phones or iPads, a local 192.168.x.x address won't work. You need to expose the homelab securely.
You can route external traffic to your local server by leveraging your Azure infrastructure to manage the DNS routing and issue SSL certificates.
Point a custom domain (e.g., bino-fantasy.com) via Azure DNS to a secure tunnel (like Cloudflare Tunnels or Tailscale Funnel) running on your homelab. This avoids opening router ports while ensuring the kids connect via standard HTTPS.
Containerization (Deployment)
To keep your homelab clean and prevent dependency conflicts, wrap the entire stack in Docker.
Write a docker-compose.yml file that spins up three containers: the React/Vue frontend (served via Nginx), the Node/Python backend API, and a worker container for the cron jobs.
Mount your SQLite .db file as a persistent Docker volume so you don't lose the kids' teams if the container restarts.
